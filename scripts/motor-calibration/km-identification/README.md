# モータゲイン $k_m$ の同定

設計モデルの入力段は $\dot\omega = (-\omega + k_m z_1)/\tau_m$ ですが、これまで $k_m = 1$ と置いたままでした。実機で $R = 1.0$ が発散し $R = 1.6$ 以降で安定したことから、この仮定が怪しいことが分かっています。$R$ は $R \to \infty$ でも $0.827$ 倍までしかゲインを下げられない弱いノブなので、余裕を作るには $k_m$ を実測して**モデルを直す**のが本筋です（[設計ドキュメント §12](../../bests/at-2026-08-16/README.md)）。

| ファイル | 役割 |
| --- | --- |
| [measure_km.ino](measure_km.ino) | 既知のデューティを階段状・ステップ状に与えて、時刻と車輪角を 100 Hz でログするスケッチ |
| [identify_km.py](identify_km.py) | ログから $G$（デューティ→車輪速度の直流ゲイン）、不感帯、むだ時間 $L_d$、時定数 $\tau_m$、そして $k_m$ を求める |

## なぜデューティを直接与えるのか

測りたいのは $u \to \omega$ ですが、その間にある下位ループ

$$
\mathrm{duty}[k] = k_p e[k] + k_i I[k],\qquad I[k] = e[k]T_s + \rho I[k-1]
$$

は**ソースから厳密に分かっている**ので、測る必要がありません。測定はモータ単体（デューティ → 車輪速度）に限定し、$u \to \mathrm{duty}$ は解析的に合成します。こうすると PI ループの過渡が同定結果に混ざりません。

## $k_m$ は 1 つの数値では表せない

下位ループはラグリードなので、$\mathrm{duty}/u$ は周波数で変わります。

$$
\frac{\mathrm{duty}}{u} \;\longrightarrow\;
\begin{cases}
k_p + k_i \dfrac{T_s}{1-\rho} = 0.065 & \text{直流} \\[2ex]
k_p = 0.025 & \text{漏れ積分の折れ点より上}
\end{cases}
$$

漏れ積分の折れ点は $(1-\rho)/T_s = 1.0$ rad/s、一方バランス制御が働くのは不安定極 $2\pi/T_p = 8.4$ rad/s の帯域です。**制御が効く帯域では $k_p$ しか残りません。** スクリプトは $k_m$ を直流と $8.4$ rad/s の両方で出力するので、**設計には後者を使ってください。**

## 測定手順

### 1. 準備

**車輪が空転するようにスタンドに乗せてください。** 40 秒ほど、正逆両方向にフルデューティまで回します。電池は充電済みのものを使ってください（$k_m$ は電源電圧に比例します）。

### 2. 書き込みと記録

`measure_km.ino` を書き込むと、3 秒後に測定が始まります。シリアル（115200 bps）を保存してください。

```bash
# pyserial で直接記録して解析まで一気に
uv run --with pyserial python scripts/motor-calibration/km-identification/identify_km.py \
    --port /dev/ttyUSB0 --save data/km-measurement.csv
```

Arduino IDE のシリアルモニタからコピーして保存しても構いません。`# BEGIN` から `# END` までが入っていれば大丈夫です。

### 3. 解析

```bash
uv run python scripts/motor-calibration/km-identification/identify_km.py data/km-measurement.csv
```

出力例（合成データでの動作確認時）:

```
 wheel        G   duty/u DC  duty/u @wb    km DC   km @wb
     A    25.99      0.0650      0.0262     1.69     0.68
     B    20.80      0.0800      0.0315     1.66     0.66
```

### 4. モデルへの反映

`@wb` 列の $k_m$ を `design_best_R14_controller.py` に入れて再設計します。連続時間モデルの 2 か所に入ります。

$$
\ddot\theta = a_\theta\theta + a_{bw}\omega - a_{bw}\,k_m\,z_1,\qquad
\dot\omega = -\frac{1}{\tau_m}\omega + \frac{k_m}{\tau_m} z_1
$$

同時に $L_d$ と $\tau_m$ も実測値に更新できます。現在の値は $L_d = 0.110$ s、$\tau_m = 0.070$ s です。

## 測定シーケンス

| 区間 | 内容 | 目的 |
| --- | --- | --- |
| 0–1 s | duty = 0 | 基準 |
| 1–16 s | duty = +0.1 … +1.0（1.5 s ずつ） | 正転の $G$ と不感帯 |
| 17–32 s | duty = −0.1 … −1.0 | 逆転の $G$ と不感帯 |
| 33–39 s | 0 → 0.6 → 0 を 3 回 | $L_d$ と $\tau_m$ |

## 実装上のポイント

- **車輪速度はスケッチで計算していません。** エンコーダ分解能は A 側で 0.187 rad/count と粗く、100 Hz で差分を取ると量子化ノイズに埋もれます。生の車輪角だけを送り、Python 側で角度に直線・積分形をあてはめて速度を出します。ステップ応答の $\tau_m$ も、速度ではなく**角度**にフィットしています。
- **MsTimer2 をあえて残しています。** D3 と D11 は Timer2 の PWM 出力で、MsTimer2 が Timer2 を占有します。バランス用スケッチと同じ PWM 波形で測るために、この条件を揃える必要があります。
- **正転と逆転で $G$ が 20 % 以上違ったら警告が出ます。** 上記のタイマ競合により、モータごとに片方向だけ PWM が正常でない可能性があるためです（[ハードウェア仕様 §12](../../../docs/specs/hardware/README.md)）。この場合はデューティと速度の関係が方向で非対称になり、線形モデルの前提が崩れます。
- 電源電圧が下がると $G$ も下がります。TB67H450 の動作下限 4.5 V に対しニッケル水素 4 本の公称は 4.8 V とマージンが薄いので、測定中に電池が減ると階段の後半だけゲインが落ちて見えます。

## 予備推定（既存データから）

新規測定の前に、[data/motor-calibration.jsonl](../../../data/motor-calibration.jsonl) から概算できます。定常部で A 輪は duty 0.360 → 9.42 rad/s、B 輪は 0.440 → 9.27 rad/s なので

$$
G_A \approx 26.2,\qquad G_B \approx 21.1\ \ [\mathrm{rad/s\ per\ duty}]
$$

これを下位ループと合成すると $k_m \approx 1.7$（直流）、$k_m \approx 0.65$（バランス帯域）です。

ただしこの数値には注意が必要です。$k_m < 1$ ならモデルより実機のアクチュエータは**弱い**ことになり、「ゲインが強すぎて発散した」という実験結果とは逆向きの示唆になります。当時の較正が速度フィードバックの効いた別スケッチで取られたものであることも含め、**この予備推定は鵜呑みにできません。** だからこそ、上記の手順で直接測る価値があります。
